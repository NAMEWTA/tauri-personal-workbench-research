# 启动失败修复与实际操作验收

目标版本：0.2.11。状态：本机验收通过；第一次 CI 安装验收发现管理员 WebView2 调试环境差异，已修正临时验收配置，待重跑当前版本 CI。

## 问题与复现

用户看到“workspace schema 2 is incompatible with the current workspace schema 1”，应用无法进入首页。实际下载并安装已发布的 0.2.10，在默认工作区放置 schema 2 数据库，通过 Playwright 连接该安装程序的真实 Tauri WebView2，复现了同样的错误；点击“重试”后仍然失败。

原因是启动入口自动复用了不受当前数据基线支持的目录。当前合并后的 Goose 基线编号为 1，不能把旧结构的编号改小、提高当前编号或者绕过校验来解决问题。之前安装 smoke 仅检查窗口句柄、进程和数据库文件，未确认首页与用户操作，因而漏检。

## 修复行为

- 自动选中的默认或最近工作区结构不受支持时，在默认工作区旁以原子创建方式保留新的 `workspace-current-N` 空目录。已有目录或同名文件均跳过。
- 只有新工作区成功启动并保存最近记录后才进入应用，下次启动继续使用它。
- 首页明确显示原工作区保留、未迁移的提示，可关闭；提示不遮挡导航。
- 手动打开不支持的工作区仍被拒绝，并恢复当前可用工作区。没有加入旧数据兼容、迁移或 schema 降级。
- 启动和恢复失败只显示安全中文摘要，内部错误保留在本地诊断日志。

## 已完成的实际操作

在同一个隔离的安装目录中安装修复版，复用曾触发错误的 schema 2 默认工作区。用 Playwright 实际操作原生 WebView2：打开首页、填写任务标题、点击“添加”、进入任务列表、正常关闭、重启，再次看到该任务。恢复提示只出现在发生恢复的启动中。检查提示、应用边界与 1280×800 窗口一致，无覆盖或底部裁切。

另只读检查了本机实际登记的工作区，确认其 Goose 版本为 2。复制该数据库到隔离目录，再用已安装的修复版成功进入首页并创建任务。复测后原数据库与测试副本的 SHA-256 均与复制前一致。该额外验证使用真实数据库结构，不仅依赖合成测试夹具。

所有人工控制与自动化操作均使用测试工作区，未对用户原有数据库执行删除、迁移或测试写入。

## 自动化与发布门禁

`pnpm check`、Go race、前端默认及单 worker 的 44 项测试、sidecar 生命周期检查、四个 viewport 的 Playwright 业务流程已通过。最终安装脚本对安装目录中的程序运行三类恢复场景、原数据库哈希验证和完整工作区/备份恢复流程，均通过；正常关闭超时直接失败。安装、覆盖升级、卸载、单实例及 sidecar 异常退出恢复也已通过。

第一次 GitHub Windows 安装验收在打开 WebView2 CDP 端口前失败，页面断言没有被跳过。GitHub runner 以高完整性进程运行时，WebView2 会忽略 `WEBVIEW2_*` 和 HKCU 调试覆盖；验收脚本现在只在 CI 且检测到高完整性时设置 `HKLM` 应用级参数，并在每次关闭后恢复原值。产品代码和发布包不携带调试参数。

发布流程增加独立的 `windows-startup-evidence` artifact，保存真实页面截图、程序版本与哈希、数据库哈希和时间。macOS 仍须生成当前版本 native/bundle evidence。最终结果见 [当前版本验收记录](../../docs/V2_ACCEPTANCE.md)，未执行或失败的项目不得记为完成。
